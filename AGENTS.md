## Project
- **Product:** Vero (VERO) by VROE Labs: verified proof-of-work identity and hiring. Workers build a portable record of real work, signed by them and the client; businesses hire from that record instead of a resume. Pre-launch: only the marketing site and waitlist are live.
- **Mode:** website (live: marketing and waitlist). The core product (identity, jobs, escrow, dual-signature records, disputes) is an app and is not built.
- **Live:** https://vero.dvpatel.workers.dev (canonical `vero.work` not yet attached) · **Repo:** https://github.com/DevPatel128/vero (public)
- **Commands (run in `website/site/`, Node 24):** `npm ci` · `npm run dev` · `npm run typecheck` · `npm run lint` · `npm test` (Playwright) · `npm run build` · `npm run preview` (local Workers runtime) · `npm run deploy` (OpenNext build and deploy) · `npm run cf-typegen` (after changing `wrangler.jsonc`). The kit's `npm run check` and `npm run e2e` do not exist here; CI runs typecheck, lint, test, build, the OpenNext build, `npm audit` and gitleaks.
- **Project rules:**
  1. `website/site/` is the only deployed code. Never move or rename it; the Cloudflare build uses that root.
  2. Merging to `main` is a production decision. A human merges.
  3. Never fabricate. Write `UNKNOWN`. Market sizes and competitor commissions are UNVERIFIED and must be labelled "internal estimate" in anything external. Any traction number is pulled live from `/api/waitlist/stats` after `/api/health` is 200, never quoted from a doc.
  4. No legal, compliance or DPDP claim, SLA or price change ships without the owner (and counsel for legal text). The live site wins over documents when they disagree (decision 2026-09-29).
  5. The waitlist token is a secret. Never return it on a duplicate join, never put email or token in a URL query or a log.
  6. D1 is reached only through `src/lib/cloudflare.ts` (binding lookup) and queried only in `src/lib/waitlist/d1-store.ts` and `src/lib/ratelimit.ts`. There are no user accounts yet; kit hard rules 3 and 4 (`forUser()`, `user_id`) apply from the first user table.
  7. Copy: follow the tone and banned words in `PRODUCT.md`. No earnings claims, no "global" or "worldwide", workers are always free, no bidding. Every product claim maps to something built or to a phase in `PRODUCT.md`.
  8. Adding analytics or error tracking requires updating `/legal/cookies` and `/legal/sub-processors` in the same PR.
  9. `website/site/AGENTS.md` is generated by `next dev`: read the Next.js docs in `node_modules/next/dist/docs/` before writing Next code.

## Hard rules (max 15; each one came from a real incident)
1. Never merge or deploy on red or skipped CI. A skipped required job is a failure.
2. Never use `--no-verify`, force-push `main`, or weaken a test to make it pass.
3. User data goes only through `src/db.ts` `forUser()`. Never touch `env.DB` elsewhere. `userId` comes only from the session.
4. `role`, `plan` and `user_id` are never client-writable. Writes use field allowlists.
5. Migrations are applied in order and checked in CI against a fresh DB. Never skip a number.
6. Never return DB errors, stack traces or internals to clients. Return stable error codes.
7. Verify webhook signature and schema, dedupe by event ID, and never trust IDs in the payload.
8. Side effects that can retry (money, orders, email, jobs) use idempotency keys.
9. Escape CSV and Excel exports (cells starting with `= + - @`).
10. No PII, tokens or money values in Sentry or PostHog.
11. Health checks test real dependencies. Never hard-code "Operational".
12. Deploy tokens carry every scope the deploy uses. Check them before a deploy, never during one.
13. Dependency major bumps get their own green CI run before merge.
14. Log a mistake in `MISTAKES.md` and add its enforcing check in the same PR.

## Coding rules
Least code that fully works. Order: skip it if nobody needs it → reuse repo code → use the platform or standard library → use an installed dependency → write one clear line → write the minimum code. No new dependency for a few lines. No wrappers or "for later" code. For bugs, grep every caller and fix the root cause once. Non-trivial logic gets one test. Mark limits with `// shortcut: <limit>, <when to upgrade>`. Split a file before 400 lines (components) or 1000 (any file). No `any` or casts. Never cut validation, security, accessibility or data-loss handling.
